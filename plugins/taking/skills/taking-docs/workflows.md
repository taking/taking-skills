# 문서 작업 절차

문서 작성 규칙은 [SKILL.md](SKILL.md)와 [style-guide.md](style-guide.md)를 따릅니다. 제출 전에는 [checklist.md](checklist.md)를 사용합니다.

## write: 새 문서 작성

1. **문서 목적과 독자 확인:** 문서가 해결할 질문과 독자를 정합니다.
2. **문서 종류 판별:** `templates/`에서 시작 템플릿을 고릅니다.
3. **기존 문서 확인:** 대상 디렉터리의 제목, 용어, 상태 표기, 관련 문서 형식을 확인합니다.
4. **핵심 내용 작성:** 목적과 범위를 먼저 밝히고, 독자가 이해하는 순서로 배치합니다.
5. **표현 형식 선택:** 문단, Dash 목록, 번호 목록, 표, Mermaid, SVG 중 내용에 맞는 형식을 선택합니다.
6. **기술적 검증:** 사실, 수치, 조건, 예외, 링크 및 구현과의 일치 여부를 확인합니다.
7. **최종 점검:** `checklist.md`와 `scripts/lint-docs.sh`로 검사합니다.

작성 중 판단:
- 문단이 길다는 이유만으로 표나 목록으로 바꾸지 않습니다. 독립 항목, 비교, 절차, 흐름이 섞여 있는지 확인합니다.
- 표로 표현할 수 있다는 이유만으로 표를 만들지 않습니다. 비교와 속성값을 같은 기준으로 보여 줄 때 사용합니다.
- 처리 순서와 상호작용이 글보다 다이어그램에서 명확해지는지 검토합니다.
- 앞에서 설명한 내용을 반복하지 말고 필요한 위치에 링크합니다.

## review: 기존 문서 검토

다음 순서로 검토합니다.

### 1. 정확성
- 사실, 수치, API, 설정, 순서, 조건, 예외가 구현 및 참조 문서와 일치하는지 확인합니다.
- 확인하지 않은 내용을 추측해 보완하지 않습니다.

### 2. 논리와 구조
- 문서 목적과 독자에게 맞는 순서인지 확인합니다.
- 문단, 목록, 표, 다이어그램의 선택이 적절한지 확인합니다.
- 중복, 과도한 소제목, 불필요한 구조화를 찾습니다.

### 3. 문체와 형식
- 번역투, 모호한 표현, 불필요한 수식어와 반복을 정리합니다.
- 문단의 응집도와 줄바꿈을 확인합니다.
- 헤딩, 코드 블록, 표, 링크 형식을 확인합니다.

### 4. 결과 제시
- 문제 위치와 문제 유형을 구체적으로 제시합니다.
- 수정 이유는 간결하게 설명합니다.
- 사용자가 수정본을 요청했다면 전체 또는 요청 범위의 Markdown을 제공합니다.
- 이미 적절한 부분은 불필요하게 고치지 않습니다.

## rewrite: 산문을 구조로 재구성

원문의 의미와 정보를 보존하면서 표현 형식을 바꿉니다.

| 원문 형태 | 우선 검토할 형식 |
| --- | --- |
| 독립적인 책임, 기능, 조건의 나열 | Dash 목록 |
| 실행 순서와 절차 | 번호 목록 |
| 속성, 설정, 비교, 항목별 값 | 표 |
| 요청과 응답의 시간순 상호작용 | Mermaid `sequenceDiagram` |
| 컴포넌트 관계와 데이터 흐름 | Mermaid `flowchart` |
| 상태와 단계 전이 | Mermaid `stateDiagram-v2` |
| Mermaid로 표현하기 어려운 정교한 구조 | SVG |
| 배경, 판단, 원인과 결과 | 일반 문단 |

절차:
1. 원문에서 사실, 값, 조건, 예외, 인과관계를 추출합니다.
2. 각 정보에 가장 적합한 표현 형식을 선택합니다.
3. 불필요한 반복과 모호한 표현을 정리합니다.
4. 변환 결과를 원문과 대조해 정보 손실과 의미 변경을 확인합니다.
5. 링크, 코드, 표, 다이어그램이 실제 내용과 일치하는지 확인합니다.

**의미 보존:** 구조 변경은 표현 형식을 바꾸는 작업입니다. 사실을 임의로 추가하거나 삭제하지 않습니다.

## polish: 기존 글 윤문 (작성자 말투 보존)

블로그, 회고, 개인 글처럼 작성자의 말투가 담긴 글에서 의미와 말투를 보존하면서 AI 문체와 번역투만 최소한으로 다듬습니다. 기술 문서를 reference-first로 재구성하는 rewrite와 목적이 다릅니다. rewrite는 형식을 바꾸고, polish는 형식을 유지한 채 표현만 손봅니다.

**최소 수정 원칙:** 자연스러운 문장은 그대로 둡니다. 수정이 필요한 부분만 바꿉니다.

보존 대상:
- 원문의 의미, 사실관계, 확신의 정도(단정과 가능성을 구분)
- 작성자의 어투, 구어체, 감정 표현, 개성 있는 문장(부자연스럽지 않은 경우)
- 인용문과 고유명사

주로 손보는 대상(상세는 [style-guide.md](style-guide.md) §8, [reference/translationese.md](reference/translationese.md)):
- 줄표(`—`), 가운뎃점(`·`) 남용
- 반복되는 부정 대구, 강조 분열문(`중요한 것은 ~`, `핵심은 바로 ~`)
- 근거 없는 과장과 추상적 평가(`새로운 가능성`, `의미 있는 인사이트`)
- 반복되는 어미와 균일한 문장 구조
- 원문에 없던 도입, 요약, 결론, 설명형 제목, 과도한 소제목

절차:
1. 원문의 의미, 사실, 확신의 정도, 말투를 파악합니다.
2. 수정 기준에 해당하는 표현만 문맥에 맞게 다듬습니다. 모든 기준을 기계적으로 적용하지 않습니다.
3. 판단이 어려운 부분은 바꾸지 않고 확인 대상으로 남깁니다.
4. 아래 자기검증을 수행하고 문제가 있으면 다시 다듬습니다.

자기검증:
- 수정 기준에 해당하는 부자연스럽거나 반복적인 표현이 남아 있는가?
- 수정이 불필요한 문장까지 바꾸지 않았는가?
- 의미, 사실관계, 확신의 정도가 달라지지 않았는가?
- 작성자의 말투와 개성이 불필요하게 사라지지 않았는가?
- 원문에 없는 사실이나 해석을 더하지 않았는가?

출력 형식:
1. **수정한 글:** 원문의 구성과 말투를 유지한 최종본
2. **주요 수정 사항과 이유:** 실제로 바꾼 표현과 이유만 간략히. 수정하지 않은 항목은 생략합니다.
3. **확인이 필요한 부분:** 의미나 사실이 불명확해 임의로 바꾸지 않은 부분. 없으면 `없음`으로 표시합니다.

## work report: 작업 보고서 작성

작업 메모, 커밋 목록, 대화 기록을 Jira 댓글이나 MR 본문, 작업 완료 보고서로 재구성합니다. 규칙의 정본은 [reference/work-report.md](reference/work-report.md)입니다. polish 가 표현만 손보는 것과 달리 구조를 다시 짭니다.

절차:
1. 사실을 먼저 모읍니다. Commit, MR 번호, 파일 경로, 함수명, 설정 키, 버전, 수치를 원문에서 뽑아 둡니다.
2. 각 변경에 대해 기존 동작, 그 문제, 고친 방식, 고른 이유를 채웁니다. 원문에 없으면 추측하지 않고 확인 대상으로 남깁니다.
3. 검증을 수준별로 나눕니다. 시험 작성, 시험 실행, 빌드와 정적 분석, 실환경 확인은 각각 다릅니다.
4. 하지 않은 검증과 범위 밖으로 남긴 항목을 따로 적습니다.
5. 정본이나 Task 와 다르게 구현한 부분이 있으면 그 차이와 근거를 적습니다.
6. [reference/work-report.md](reference/work-report.md) §5 의 절 순서로 배치하고, 해당하지 않는 절은 뺍니다.
7. 아래 자기검증을 수행합니다.

자기검증:
- 원문의 사실, 수치, 식별자가 모두 남아 있는가?
- 변경마다 이유가 적혀 있는가?
- 검증 수준을 섞어 적지 않았는가? 하지 않은 검증을 통과로 쓰지 않았는가?
- 미검증 항목과 범위 밖 항목이 구분되는가?
- 원문에 없는 효과나 사실을 더하지 않았는가?

출력 형식:
1. **보고서:** 바로 붙여 넣을 수 있는 Markdown
2. **추가 확인 사항:** 기술적으로 의심스러워 본문을 고치지 않고 남긴 것. 없으면 `없음`
