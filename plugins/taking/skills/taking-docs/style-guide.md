# 기술 문서 스타일 가이드

`SKILL.md`의 문서 작성 원칙을 구체화합니다. 문서 작성 규칙의 정본은 이 파일이며, `SKILL.md`는 핵심 원칙과 작업별 참조 경로를 안내합니다. 코드 주석 규칙은 `code-comments/style-guide.md`가 별도 정본입니다.

원칙의 우선순위는 **기술적 정확성 → 명확성 → 논리적 완결성 → 가독성 → 간결성**입니다. 간결하게 만들기 위해 사실, 조건, 예외, 근거를 제거하지 않습니다.

## 목차

- 문서 구조와 개요
- 문단과 줄바꿈
- 문장 작성 원칙
- 문단, 목록, 표 선택
- Mermaid와 SVG
- 문서 종류별 구성
- 용어와 기술적 정확성
- AI 문체와 표현
- 제목과 형식
- 링크와 참조
- 기존 문서와의 일관성

## 1. 문서 구조와 개요

문서의 목적과 독자에 맞는 구조를 선택합니다. 모든 문서에 같은 골격을 강제하지 않습니다.

- 독자가 문서의 목적과 범위를 빠르게 파악할 수 있도록 처음에 짧은 개요를 둡니다.
- `TL;DR`, `Overview`, `Summary` 중 문서 성격에 맞는 제목을 선택합니다. 짧은 문서에 별도 개요 섹션을 억지로 추가하지 않습니다.
- 개요에는 문서가 다루는 대상, 범위, 핵심 내용을 담습니다. 배경 전체를 반복하지 않습니다.
- 본문은 독자가 이해하고 작업하는 데 필요한 순서로 배치합니다.
- 일반적인 기술 설명은 `What → How → Why`를 기본으로 하되, 설계 배경이 핵심인 문서에서는 `Why`를 먼저 둘 수 있습니다.
- 같은 사실을 여러 섹션에서 반복하지 않습니다. 다시 필요하면 해당 섹션으로 링크합니다.
- 도입부, 요약, 결론을 기계적으로 붙이지 않습니다. 윤문할 때 원문에 없던 도입이나 결론 문단을 새로 만들지 않습니다.

## 2. 문단과 줄바꿈

**가독성은 줄바꿈의 개수가 아니라 정보의 배치와 문단의 응집도로 결정됩니다.**

- 서로 밀접한 문장은 하나의 문단으로 묶습니다.
- 한 문단에는 하나의 핵심 주제를 담습니다.
- 문단 안에서 편집기 폭에 맞춰 강제로 줄을 나누지 않습니다. Markdown 원문에서는 한 문단을 한 줄로 작성합니다.
- 문단 사이에는 빈 줄 하나를 둡니다. 연속된 빈 줄은 사용하지 않습니다.
- 주제나 논점이 바뀌면 문단을 나눕니다. 한 문장마다 빈 줄을 넣지 않습니다.
- 문단 길이를 문장 수나 글자 수로 기계적으로 제한하지 않습니다. 길어졌다는 이유만으로 목록이나 표로 바꾸지 않습니다.
- 긴 문단에 독립된 항목, 비교, 단계, 조건이 섞여 있을 때 해당 정보 유형에 맞는 구조로 바꿀지 검토합니다.
- 서로 다른 논점을 억지로 한 문단에 합치지 않습니다.
- 문단의 길이와 구조를 억지로 균일하게 맞추지 않습니다. 원문의 자연스러운 흐름과 강조점을 유지합니다.

**지양**

```markdown
SAN이 맞지 않아 생긴 실패가 `reason="other"`로 집계됩니다.

기존 분류 함수는 오류 문자열을 비교합니다.

Go가 반환하는 오류 문구와 비교 문자열이 다릅니다.
```

**권장**

```markdown
SAN이 맞지 않아 생긴 실패가 `reason="other"`로 집계됩니다. 기존 분류 함수는 오류 문자열을 직접 비교하지만, Go가 반환하는 오류 문구와 비교 문자열이 달라 정상적으로 분류하지 못합니다.
```

## 3. 문장 작성 원칙

기술 문장은 짧게 쓰는 것보다 정확하고 명확하게 쓰는 것이 중요합니다. ASD-STE100의 명확성, 일관성, 모호성 제거 원칙을 참고하되 공식 표준의 완전한 준수를 목표로 하지 않습니다. 시스템 제약, API 계약, 보안 요구처럼 지켜야 하는 수준이 있는 문장은 RFC 2119 키워드와 ASD-STE100 원칙을 함께 적용합니다([reference/requirement-levels.md](reference/requirement-levels.md)).

- 행위 주체와 동작을 독자가 알 수 있게 씁니다. 문맥상 주체가 명확한 한국어 문장에서 불필요한 주어를 반복하지 않습니다.
- 가능하면 피동 표현보다 자연스러운 능동 표현을 사용합니다. 실제 행위 주체를 확인할 수 없으면 임의로 만들어 넣지 않습니다.
- 한 문장에 여러 논점을 억지로 연결하지 않습니다.
- 짧은 문장을 기계적으로 연속해서 쓰지 않습니다. 밀접한 내용은 자연스럽게 연결합니다.
- 접속사는 논리 관계를 나타낼 때만 사용합니다.
- 조건, 예외, 범위, 실패 동작을 모호하게 표현하지 않습니다.
- `가능하다`, `적절히`, `필요시`, `일반적으로`처럼 범위가 불분명한 표현은 구체적인 조건으로 바꿉니다. 근거가 없으면 임의로 구체화하지 않습니다.
- 문장마다 종결어미를 억지로 바꾸지 않습니다. 자연스러운 흐름과 문서 전체의 일관성을 우선합니다.

## 4. 문단, 목록, 표 선택

문단, Dash 목록, 번호 목록, 표 중 해당 정보를 가장 정확하고 읽기 쉽게 전달하는 형식을 선택합니다. 표나 목록으로 바꿀 수 있다는 이유만으로 구조를 바꾸지 않습니다.

### 4.1 일반 문단

다음 내용은 문단으로 설명하는 편이 자연스럽습니다.

- 설계 배경과 판단 근거
- 원인과 결과가 밀접하게 연결된 설명
- 트레이드오프와 선택 이유
- 맥락이 필요한 기술적 설명
- 독립 항목으로 나누면 의미가 끊기는 내용

### 4.2 Dash 목록

서로 독립된 항목이나 한 대상이 수행하는 여러 동작을 나열할 때 Dash (`-`) 목록을 사용합니다.

- 독립된 항목이 3개 이상이면 목록 사용을 검토합니다. 1~2개라면 문장으로 쓰는 편이 자연스러운지 먼저 판단합니다.
- 긴 설명에 독립된 책임, 기능, 조건, 결과가 섞여 있으면 핵심 설명 뒤에 목록을 둡니다.
- 항목마다 하나의 핵심 내용을 담습니다.
- 가능하면 `**핵심 키워드:** 설명` 형태로 항목의 주제를 먼저 보여 줍니다.
- 항목 설명은 간결하게 작성하되, 정확성에 필요한 조건과 예외는 유지합니다.
- 순서가 중요하지 않은 항목에 번호를 붙이지 않습니다.
- 목록 안의 중첩 목록은 꼭 필요한 경우에만 사용합니다.
- 원인과 결과, 배경과 판단처럼 논리적 연결이 중요한 내용은 목록으로 쪼개지 않습니다.
- 모든 문장을 목록으로 바꾸거나, 한 문장짜리 목록을 반복하지 않습니다.

### 4.3 번호 목록

실행 순서, 설치 절차, 마이그레이션 단계처럼 순서가 결과에 영향을 주는 경우 번호 목록을 사용합니다. 순서가 있는 작업을 표로 대체하지 않습니다.

### 4.4 표

같은 기준으로 여러 대상을 비교하거나, 속성과 값을 빠르게 찾아야 할 때 표를 사용합니다.

적합한 예:
- 컴포넌트별 역할과 책임
- 설정 키, 기본값, 설명
- API 요청 및 응답 필드
- 오류 코드와 처리 방식
- 대안별 장단점
- 지원 여부와 제약 사항

표 작성 규칙:
- 비교 대상에는 같은 기준과 같은 표현 수준을 적용합니다.
- 열 제목은 짧고 구체적으로 작성합니다.
- 셀에는 핵심 구나 짧은 문장을 사용합니다. 모든 셀을 억지로 명사형으로 줄이지 않습니다.
- 조건, 예외, 계약 의미가 축약으로 사라지면 설명을 유지합니다.
- 한두 행만 있는 작은 표는 문장이나 목록이 더 명확한지 검토합니다.
- 본문과 표가 같은 정보를 반복하지 않도록 역할을 나눕니다.
- 한 표 안에서 용어, 구분자, 값 표기 방식을 통일합니다.
- 성격이 다른 내용을 한 표에 억지로 모으지 않습니다. 열 제목이 일부 행에만 맞으면 표를 나눕니다.
- 빈 표, 빈 행, 의미 없는 구분선을 남기지 않습니다.

## 5. Mermaid와 SVG

순서, 상호작용, 상태 변화, 컴포넌트 관계를 글로 설명하는 것보다 다이어그램으로 보여 주는 편이 명확할 때 다이어그램을 사용합니다. 다이어그램은 필수 장식이 아닙니다.

### 5.1 Mermaid 선택

Mermaid를 기본 도구로 사용합니다. 텍스트 기반이라 변경 이력을 추적하고 유지보수하기 쉽습니다.

| 표현할 내용 | Mermaid 형식 |
| --- | --- |
| 처리 흐름, 조건 분기, 의존 관계 | `flowchart` |
| 컴포넌트 간 요청과 응답 | `sequenceDiagram` |
| 상태와 상태 전이 | `stateDiagram-v2` |
| 객체와 타입 관계 | `classDiagram` |
| 데이터 엔터티 관계 | `erDiagram` |

다이어그램을 검토할 상황:
- 여러 단계로 이어지는 처리 과정
- 조건에 따른 분기와 예외 흐름
- 여러 컴포넌트의 책임과 연결
- 요청, 응답, 이벤트의 시간순 상호작용
- 상태 전이와 라이프사이클
- 여러 주체가 참여하는 작업 순서

간단한 두 단계 설명이나 문장 하나로 충분히 전달되는 관계는 다이어그램으로 만들지 않습니다.

### 5.2 다이어그램 품질

- 노드와 연결선의 의미가 명확해야 합니다.
- 화살표 방향과 데이터 흐름을 실제 동작에 맞춥니다.
- 노드 이름은 실제 컴포넌트, 상태, 작업 이름을 사용합니다.
- 노드와 연결을 필요 이상으로 늘리지 않습니다.
- 복잡한 다이어그램은 논리적 단위로 나눕니다.
- 라벨은 짧고 구체적으로 작성합니다.
- 다이어그램과 본문, 코드, 표의 값이 일치하는지 확인합니다.
- 다이어그램으로 표현한 내용을 본문에서 그대로 반복하지 않습니다. 단, 중요한 조건, 제약, 설계 근거는 본문에 남깁니다.
- 다이어그램만으로 정확히 전달하기 어려운 내용은 보충 설명을 둡니다.

### 5.3 SVG 선택

Mermaid로 표현하기 어렵거나 정교한 배치, 계층, 시각적 강조가 필요한 경우에만 SVG를 사용합니다.

- Mermaid로 충분히 표현할 수 있으면 SVG를 별도로 만들지 않습니다.
- SVG는 꾸밈보다 정보 전달과 구조를 우선합니다.
- 텍스트, 연결선, 화살표, 레이블은 실제 동작과 일치해야 합니다.
- SVG를 수정할 원본이 무엇인지 문서나 저장소 구조에서 알 수 있게 관리합니다.
- 이미지로만 정보를 전달하지 않습니다. 중요한 의미와 제약은 본문에도 텍스트로 남깁니다.

## 6. 문서 종류별 구성

템플릿은 시작점입니다. 실제 저장소의 기존 문서 관례와 독자 목적을 확인한 뒤 필요한 섹션만 사용합니다.

| 문서 종류 | 주로 다룰 내용 |
| --- | --- |
| ADR | Context, Decision, Alternatives, Consequences |
| Architecture | Overview, Responsibilities, Components, Data Flow, Trade-offs |
| Design | Context, Goals/Non-Goals, Design, Alternatives, Risks |
| API / gRPC | Overview, 계약, 요청과 응답, 오류, 예제 |
| Kafka | Topic, Event Schema, Delivery Semantics, Consumer |
| Runbook | 사전 조건, 순서가 있는 작업, 검증, 롤백 |
| Troubleshooting | 증상, 원인, 진단, 조치, 에스컬레이션 |
| Overview | 목적, 범위, 주요 개념, 관련 문서 |
| Communication | Transports, Sequence, Failure handling |
| Security | Trust Boundary, Identity/Auth, Threats & Mitigations, Deferred |
| README | 소개, 요구사항, 설치와 실행, 디렉터리, 설정 |
| Postmortem | 요약, 영향 범위, 타임라인, 근본 원인, 액션 아이템 |

ADR은 결정의 근거와 대안, 결과를 충분히 설명합니다. ADR 전체를 표나 다이어그램으로 바꾸지 않습니다. 표는 대안 비교에, 다이어그램은 구조나 흐름 설명에 사용합니다.

## 7. 용어와 기술적 정확성

- 같은 개념에는 문서 전체에서 같은 용어를 사용합니다.
- 프로젝트에서 이미 쓰는 명칭, API, 식별자, 설정 키, 파일명은 임의로 바꾸지 않습니다.
- 업계에서 통용되는 기술 용어는 무리하게 번역하지 않습니다.
- 중요한 개념은 첫 등장에 짧게 설명하고 이후 같은 용어를 사용합니다.
- 번역하면 의미가 달라지는 용어는 원어를 유지합니다.
- 구현에서 확인한 사실, 설계 의도, 추론을 구분합니다.
- 확인되지 않은 동작, 수치, 성능, 호환성, 보안 특성을 만들어 내지 않습니다.
- 윤문과 구조 변경 과정에서 조건, 부정, 예외, 순서, 수치, 버전, API 의미를 바꾸지 않습니다.
- 불명확한 부분은 추측해 채우지 말고 확인이 필요한 사항으로 표시합니다.

## 8. AI 문체와 표현

표현을 기계적으로 금지하기보다 문맥에서 정보 없이 문장을 부풀리는지 판단합니다. 어떤 패턴이든 빈도만 보고 0으로 몰아내면 교정이 아니라 문체 삭제입니다. 실제로 대비나 강조가 필요한 곳은 남깁니다. 집단 통계로 참인 규칙도 개인 글에 기계적으로 들이대면 그 사람의 말투를 지웁니다.

| 지양하는 표현 | 권장하는 처리 |
| --- | --- |
| `이를 통해`, `이로써` | 앞뒤 문장을 자연스럽게 연결하거나 삭제 |
| `다음과 같다` | 바로 표나 목록 제시 |
| `효율적으로`, `손쉽게`, `원활하게` | 실제 동작이나 측정값으로 대체하거나 삭제 |
| `수행한다`, `지원한다`, `제공한다` | 만든다, 읽는다, 보낸다, 검증한다 등 실제 동작으로 표현 |
| `다양한`, `여러 가지` | 실제 항목을 나열하거나 범위를 명시 |
| `적절히`, `필요시`, `일반적으로` | 조건을 구체화하거나 불확실성을 표시 |
| `의 핵심`, `전환점`, `정수` | 실제 역할과 동작을 서술 |
| `구조적 일관성을 보장한다` | 무엇이 일치하고 어떻게 보장되는지 설명 |

### 8.1 긴 대시와 문장 부호

- 문장 사이를 연결하는 긴 대시(`—`)는 사용하지 않습니다. 마침표, 콜론, 괄호로 바꿉니다.
- 라벨과 설명은 필요할 때 `: `로 구분합니다.
- 고유명사, 공식 문서 제목, 코드, URL의 표기는 임의로 변경하지 않습니다.
- 가운뎃점(`·`)은 일반적인 나열에서 쉼표로 바꿉니다. 고유명사와 공식 제목은 원문을 유지합니다.
- 숫자 범위와 코드의 하이픈은 긴 대시 금지 규칙과 구분합니다.
- 영어식으로 연결 어미나 접속어 뒤에 쉼표를 습관적으로 넣지 않습니다. 한국어는 접속 뒤 쉼표가 필수가 아닙니다. 다만 쉼표 개수를 세어 기계적으로 지우지는 않습니다.

### 8.2 부정 대구

`단순히 X가 아니라 Y`, `X를 넘어 Y`, `X일 뿐 아니라 Y이기도 하다` 같은 표현을 습관적으로 사용하지 않습니다. 실제 대비가 핵심 정보일 때는 허용합니다. 대비가 필요하지 않으면 핵심 동작이나 사실을 직접 씁니다.

### 8.3 과장과 근거 없는 범위

- 실제 개수와 관계없이 세 항목으로 맞추지 않습니다.
- `A부터 Z까지`처럼 실제 범위를 확인할 수 없는 표현을 쓰지 않습니다.
- `핵심`, `혁신`, `전환점`, `새로운 가능성`, `의미 있는 인사이트`처럼 평가만 하는 표현은 구체적인 사실로 바꿉니다.
- `역할을 한다`, `자리매김`, `기여한다`처럼 실제 한 일 대신 공허하게 평가하는 표현은 실제 동작으로 바꿉니다.
- `결론적으로`, `~라는 것이다`, `~인 셈이다`처럼 상투적으로 끝맺는 표현은 사실이나 수치로 맺습니다.
- 근거 없는 성능, 안정성, 확장성 주장을 추가하지 않습니다.

### 8.4 조어와 어려운 표현

- 저장소나 업계에서 쓰지 않는 추상 명사를 새로 만들지 않습니다.
- 여러 대상을 묶는 말이 필요하면 실제 항목을 나열하거나 익숙한 표현을 사용합니다.
- 쉬운 표현으로 의미를 정확히 전달할 수 있으면 불필요하게 어려운 동사를 선택하지 않습니다.
- 다만 정확한 기술 용어를 단순히 어렵다는 이유로 바꾸지 않습니다.

### 8.5 강조와 형식

- 이모지를 제목 장식이나 섹션 구분자로 사용하지 않습니다.
- 굵은 글씨는 핵심 용어나 중요한 판단을 강조할 때만 사용합니다.
- 한 문단에서 여러 표현을 동시에 굵게 처리하지 않습니다.
- 곡선 따옴표는 프로젝트의 인용 관례를 따르되, 코드와 명령어 표기는 원문을 유지합니다.

### 8.6 강조 분열문

`중요한 것은 ~라는 점이다`, `핵심은 바로 ~`, `주목해야 할 점은 ~` 같은 분열 구문으로 문장을 비틀어 강조하지 않습니다. 강조 구문을 빼도 의미가 전달되면 핵심 내용을 바로 서술합니다. 실제로 초점을 옮기거나 대비해야 하는 경우에만 사용합니다.

| 지양하는 표현 | 권장하는 처리 |
| --- | --- |
| 중요한 것은 캐시 무효화라는 점이다. | 캐시를 무효화해야 합니다. |
| 핵심은 바로 재검증 비용이다. | 재검증에 매 요청 20ms가 듭니다. |
| 주목해야 할 점은 처리 순서다. | 처리 순서가 결과를 바꿉니다. |

## 9. 제목과 헤딩

- 한 문서에는 H1을 하나만 둡니다.
- H2와 H3를 순서대로 사용하고 제목 단계는 건너뛰지 않습니다.
- 헤딩은 섹션의 주제를 식별하는 짧고 구체적인 표현으로 작성합니다.
- 명사구를 기본으로 하되 튜토리얼의 행동형, FAQ의 질문형 등 문서 목적에 맞는 예외를 허용합니다.
- 제목을 설명형 완전 문장으로 만들지 않습니다. 모든 문단에 소제목을 기계적으로 붙이지 않습니다.
- 짧은 내용만 있는 소제목은 상위 섹션에 합칠 수 있는지 검토합니다.
- 제목만 읽어도 문서의 흐름과 범위를 파악할 수 있어야 합니다.

## 10. 링크와 참조

- 외부 표준, 공식 API, 명세가 정본이면 필요한 설명만 남기고 원문 링크를 제공합니다.
- 내부 문서는 실제 경로와 앵커가 존재하는지 확인합니다.
- 관련 문서는 문서 하단의 `References` 또는 저장소 관례에 맞는 섹션에 모읍니다.
- 원문에 없는 절 번호나 인용 위치를 만들어 내지 않습니다.
- 링크 텍스트는 대상 문서의 내용을 알 수 있게 작성합니다.

## 11. 기존 문서와의 일관성

기존 저장소에 새 문서를 추가하거나 수정할 때는 템플릿보다 실제 문서 관례를 먼저 확인합니다.

- 같은 디렉터리의 문서에서 제목, 상태, 날짜, 관련 문서 형식을 확인합니다.
- 짝을 이루는 문서(설계 문서와 ADR 등)는 같은 개념에 같은 용어를 사용합니다.
- 기존 문서의 용어가 여러 개라면 사용 빈도만으로 결정하지 말고 문맥과 정본 문서를 확인합니다.
- 기존 관례가 기술적으로 잘못되었거나 이번 변경과 충돌하면 차이를 명시하고 일관된 방향을 제안합니다.
- 템플릿과 실제 관례가 다르면 차이를 확인한 뒤 독자와 저장소의 일관성에 맞는 쪽을 선택합니다.
