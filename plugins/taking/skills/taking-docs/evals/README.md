# evals : 스킬 회귀 시나리오

이 스킬이 실제로 걸리는지, 걸린 뒤 규칙을 적용하는지 확인합니다. 자동 실행 장치는 없습니다. 새 세션에 프롬프트를 그대로 주고 `expected`와 대조합니다.

새 문체 규칙은 근거 없이 넣지 않습니다. 근거 없는 규칙은 그 자체가 새 오염원이 됩니다. 규칙을 추가하면 여기에 걸리는지 확인하는 시나리오를 함께 둡니다.

## 목차

- 실행 방법
- 채점
- 1. 설계 서사와 유지할 사실 가르기
- 2. 종결 형태
- 3. 산문 → 구조
- 4. 긴 대시, 부정 대구, 의의 과장
- 5. 문단, 목록, 다이어그램 선택
- 6. 윤문: 작성자 말투 보존
- 7. 작업 보고서: 검증 수준과 변경 이유
- 8. 번역투 문법과 접속어 몰림
- 9. 평서문을 요구문으로 (RFC 2119)
- 10. `~할 수 있다`: 허용과 가능성 구분

## 실행 방법

1. 새 세션(스킬이 로드되는 환경)을 엽니다. 같은 세션에서 돌리면 규칙이 이미 컨텍스트에 있어 통과가 보장되고 아무것도 시험하지 못합니다.
2. `prompt`를 그대로 붙입니다. `expected`는 주지 않습니다.
3. 프롬프트 끝에 아래 두 줄을 붙여 스킬 발견 여부를 함께 받습니다.

```text
SKILL_INVOKED: (Skill 도구로 호출한 스킬 이름. 없으면 none)
FILES_READ: (읽은 스킬 문서 경로. 없으면 none)
```

**평가는 부작용이 없어야 합니다.** 모든 프롬프트에 `파일을 수정하지 말고 결과만 보고해 줘`를 넣습니다. 이 조건이 없으면 에이전트가 `고쳐 줘`를 저장소 반영으로 읽습니다(실제로 그랬습니다).

## 채점

| 축 | 무엇을 보나 |
| --- | --- |
| 발견 | `SKILL_INVOKED`에 `taking-docs`가 있나 |
| 도달 | `FILES_READ`에 `code-comments/` 아래 파일이 있나 (참조가 1단계로 유지되는지의 지표) |
| 적용 | `expected`를 만족하고 `must-not`이 없나 |
| 인용 | 근거로 든 파일, 행 번호가 실제로 존재하나 (추측 금지 규칙) |

`expected`를 못 맞히면 **규칙이 없는 것인지, 있는데 안 읽힌 것인지** 먼저 구분합니다. 후자면 `SKILL.md` 참고 자료의 링크를 의심합니다.

## 1. 설계 서사와 유지할 사실 가르기

통째로 지우는지가 아니라 **가려내는지**를 봅니다. 1문단은 UX 근거(소스에서 빼는 것), 2문단은 성능 비용 사실(남기는 것)입니다.

**prompt**

````text
아래 주석을 리뷰해 줘. 파일을 수정하지 말고 결과만 보고해 줘.

```ts
/**
 * 사이드바는 즐겨찾기만 보여준다. 조회 가능한 종류가 100개를 넘어 전부 나열하면 매번 찾아야
 * 한다. 나머지는 아래 `전체 리소스 종류 보기`로 열어 고른다. *
 * 펼친 묶음의 종류만 인스턴스 수를 센다. 카운트는 종류마다 클러스터를 한 번 훑는 일이라,
 * 전부 세면 화면을 열 때마다 조회가 수십 번 나간다(서버가 가상 스레드로 병렬 처리하지만
 * 클러스터가 받는 부하는 그대로다). */ export function KindSidebar({ ... })
```
````

**expected**

- 1문단의 UX 근거(`100개를 넘어 매번 찾아야 한다`, `전체 리소스 종류 보기로 열어 고른다`)를 빼라고 합니다.
- **2문단의 비용 사실은 남깁니다.** 카운트가 종류마다 클러스터를 훑는다는 것은 코드에 없고, 모르면 "전부 세도 되겠지"로 잘못 고칩니다.
- 남길 문장을 1~2줄로 줄입니다.

**must-not**

- 두 문단을 모두 지웁니다(성능 근거는 정본 규칙이 문서화하라고 지정한 항목입니다).
- 두 문단을 모두 남기고 표현만 다듬습니다.
- `서버가 가상 스레드로 병렬 처리한다` 같은 구현 세부를 새로 덧붙입니다.

## 2. 종결 형태

**prompt**

````text
아래 주석을 이 저장소 규칙에 맞게 고쳐 줘. 파일을 수정하지 말고 결과만 보고해 줘.

```ts
// 행 클릭과 겹치면 상세가 두 번 열린다. // 앞서 적어 둔 이름이 남으면 확인 절차가 없는 것과 같다. // 브라우저가 막을 수 있다(권한, 비보안 출처).
```
````

**expected**

- 짧은 사실을 명사형으로 끊습니다(`~ 열림`, `~ 같음`, `~ 있음` 등). 존댓말로 써도 되지만, 짧은 사실엔 명사형이 낫습니다.
- 종결어미를 길게 붙이면 정당화 절이 딸려온다는 근거를 듭니다.
- 세 줄의 사실(전파 중단, 입력 초기화, 실패 가능)은 그대로 유지합니다.

**must-not**

- 사실 뒤에 정당화 절을 붙여 문장을 늘립니다.
- 세 줄을 똑같은 종결어미로 3줄 연속 통일합니다.
- 사실을 지웁니다(코드 재진술이 아니라 코드에 없는 정보입니다).

## 3. 산문 → 구조

**prompt**

```text
아래 문단을 기술 문서에 맞게 고쳐 줘. 파일을 수정하지 말고 결과만 보고해 줘.

"에이전트는 두 가지 전송로를 사용합니다. 첫 번째는 core라고 불리는 터널이며 이를 통해
apiserver 프록시와 자원 조회가 수행됩니다. 두 번째는 events이고 Kafka를 통해 이벤트를
효율적으로 전달하는 역할을 담당합니다. 또한 두 전송로는 모두 mTLS로 보호됩니다."
```

**expected**

- 번역투, 포장어를 제거합니다. 톤은 존댓말을 유지합니다(기본 톤 §2).
- `이를 통해`, `효율적으로`, `역할을 담당합니다`, `또한`을 지웁니다.
- `첫 번째는`, `두 번째는` 서수 나열을 지웁니다(이름이 있습니다).
- `조회가 수행됩니다` 수동태를 능동으로 바꿉니다.
- 독립 항목 두 개를 표로 만들지, 짧은 문단으로 유지할지 내용에 맞게 판단합니다.
- 표를 선택했다면 같은 기준으로 비교하고, 문단을 선택했다면 불필요한 목록화를 피합니다.

항목이 둘뿐이라는 이유만으로 표를 강제하지 않습니다. 표, 목록, 문단 중 가장 명확한 형식을 선택하는지가 평가 기준입니다.

**must-not**

- 문단 형태를 유지한 채 낱말만 바꿉니다(서수, 수동태가 남습니다).
- 원문에 없는 사실(포트, 재시도 정책, 성능 수치)을 채워 넣습니다.
- 전송로 이름(`core`, `events`)이나 담당 범위를 바꿉니다.

## 4. 긴 대시, 부정 대구, 의의 과장

§8.1~8.3 규칙이 실제로 걸리는지 봅니다. 한 문단에 긴 대시, 부정 대구, 억지 3개 나열, 거짓 범위, 의의 과장을 모두 심었습니다.

**prompt**

```text
아래 문단을 기술 문서에 맞게 고쳐 줘. 파일을 수정하지 말고 결과만 보고해 줘.

"이 캐시는 단순한 성능 최적화가 아니라 시스템의 핵심이다 — 모든 요청이 거쳐 가는 지점이기 때문이다. 확장성, 안정성, 응답성을 모두 제공하며, 작은 설정부터 대규모 트래픽까지 아우른다."
```

**expected**

- 긴 대시(`—`)를 마침표나 괄호로 바꿉니다.
- 부정 대구(`단순한 ~가 아니라 ~의 핵심이다`)를 지우고, 캐시가 실제로 하는 일을 직접 서술합니다.
- 억지 3개 나열(`확장성, 안정성, 응답성`), 거짓 범위(`작은 설정부터 대규모 트래픽까지`)를 실제 사실로 바꾸거나 지웁니다.
- 의의 과장(`시스템의 핵심`)을 뺍니다.

**must-not**

- em-dash를 그대로 둡니다.
- `단순한 ~가 아니라` 대구를 유지한 채 낱말만 바꿉니다.
- 거부절(`단순한 성능 최적화가 아니라`)만 남기고 뒤 절을 지웁니다.
- 원문에 없는 성능 수치(캐시 적중률, 지연 ms)를 지어냅니다.

## 5. 문단, 목록, 다이어그램 선택

**prompt**

```text
다음 설명을 기술 문서에 맞게 정리해 줘. 파일은 수정하지 말고 결과만 보고해 줘.

"Cluster Agent는 Service API에 연결하고 인증을 수행한다. 연결이 완료되면 core stream에서 명령을 받고 Kubernetes 리소스를 처리한다. 처리 결과는 events stream으로 보낸다. 연결이 끊기면 재연결을 시도한다."
```

**expected**

- 문단을 무조건 짧게 자르지 않고, 핵심 소개와 독립적인 작업 목록을 상황에 맞게 구분합니다.
- 순서가 중요한 부분만 번호 목록 또는 Mermaid로 표현합니다. 단순한 나열에 다이어그램을 강제하지 않습니다.
- Dash 목록을 쓴다면 각 항목의 핵심 동작을 분명하게 표현합니다.
- 원문에 없는 인증 방식, 재시도 정책, 포트, 데이터 흐름을 추가하지 않습니다.

**must-not**

- 모든 문장을 개별 문단으로 나눕니다.
- 모든 내용을 표로 바꿉니다.
- 짧은 흐름을 무조건 SVG로 만듭니다.
- 원문에 없는 구현 세부를 추측해 추가합니다.

## 6. 윤문: 작성자 말투 보존

polish 모드가 AI 문체만 걷어내고 작성자의 구어체와 말투는 남기는지 봅니다. 블로그 글에 긴 대시, 부정 대구, 강조 분열문, 과장, 이중피동, 상투 결론을 구어체와 섞어 심었습니다.

**prompt**

```text
아래 블로그 글을 자연스럽게 다듬어 줘. 파일은 수정하지 말고 결과만 보고해 줘.

"이번에 캐시를 새로 붙였는데 솔직히 반신반의했다. 근데 이건 단순한 성능 개선이 아니라 사용자 경험의 전환점이었다 — 응답이 확 빨라졌거든. 중요한 것은 바로 체감 속도라는 점이다. 앞으로도 다양한 가능성을 열어줄 거라고 본다. 이런 개선은 계속 적용되어질 것 같다. 결론적으로 캐시는 꼭 써야 한다는 것이다."
```

**expected**

- 긴 대시(`—`)를 마침표나 괄호로 바꿉니다.
- 부정 대구(`단순한 ~가 아니라 ~의 전환점`)와 강조 분열문(`중요한 것은 바로 ~라는 점이다`)을 풀어 직접 서술합니다.
- 과장(`전환점`, `다양한 가능성을 열어줄`)을 줄이거나 원문의 사실(응답이 빨라졌다)로 바꿉니다.
- 이중피동(`적용되어질`)을 단일 피동이나 능동(`적용될`, `적용할`)으로 바꿉니다.
- 상투 결론(`결론적으로 ~라는 것이다`)을 빼고 작성자의 말투나 사실로 끝맺습니다.
- 작성자의 구어체와 말투(`솔직히 반신반의했다`, `빨라졌거든`)는 유지합니다. 존댓말로 바꾸지 않습니다.
- 수정본, 주요 수정 사항, 확인이 필요한 부분으로 보고합니다.

**must-not**

- 전체를 존댓말 기술 문서 톤으로 바꿔 작성자 말투를 지웁니다.
- `반신반의했다`, `빨라졌거든` 같은 자연스러운 구어체까지 평문으로 바꿉니다.
- 원문에 없는 수치(지연 ms, 캐시 적중률)를 지어냅니다.
- 긴 대시, 강조 분열문, 이중피동(`~되어질`), 상투 결론(`~라는 것이다`)을 그대로 둡니다.

## 7. 작업 보고서: 검증 수준과 변경 이유

work report 모드가 문장만 다듬지 않고 구조를 다시 짜는지, 검증 수준을 섞지 않는지 봅니다. 원문은 작업 메모 형태이고, 구현과 검증이 섞여 있으며 변경 이유가 빠져 있습니다.

**prompt**

```text
아래 작업 메모를 Jira 댓글로 정리해 줘. 파일은 수정하지 말고 결과만 보고해 줘.

"세션 상한을 48로 켰고 지표도 추가함. MR !213 병합됨. InteractiveSessionLimiter 에 접근자 두 개 추가하고 InteractiveMetrics 에서 MultiGauge 로 냄. 테스트 썼고 devstack 에서 조회도 해봄. 49번째 거절되는 건 단위 테스트로만 확인. 클러스터 여러 대는 못 해봄."
```

**expected**

- 작업 완료와 병합 현황을 먼저 적고 MR 번호를 보존합니다.
- 시험 작성, 시험 실행, 실환경 확인을 구분합니다. 49번째 거절은 단위 시험으로만 확인했다고 적습니다.
- 클러스터 여러 대를 재지 못한 것을 미검증 항목으로 따로 적습니다.
- 변경 이유가 원문에 없으므로 추측해 채우지 않고 추가 확인 사항으로 남깁니다.
- 함수명과 클래스명(`InteractiveSessionLimiter`, `InteractiveMetrics`, `MultiGauge`)을 그대로 씁니다.
- 보고서와 추가 확인 사항으로 나누어 보고합니다.

**must-not**

- `devstack 에서 조회도 해봄`을 실환경 검증 완료로 확장해 적습니다.
- 상한 48을 고른 이유를 원문에 없는 근거로 지어냅니다.
- 성능 개선, 안정성 향상 같은 효과를 원문에 없이 추가합니다.
- 미검증 항목을 빼거나 검증 절에 섞어 적습니다.
- 메모를 문장만 다듬어 한 문단으로 내보냅니다.

## 8. 번역투 문법과 접속어 몰림

`translationese.md`에 추가한 항목(이중피동, `~에 있어서`, 주어 없는 과장, 공허한 기여어, 접속어 몰림)이 실제로 걸리는지 봅니다. 한 문단에 모두 심었고, 모듈의 실제 동작은 주지 않아 추측 유도도 함께 봅니다.

**prompt**

```text
아래 문단을 기술 문서에 맞게 고쳐 줘. 파일은 수정하지 말고 결과만 보고해 줘.

"이 모듈은 시스템에 있어서 핵심 역할을 한다. 또한 최근 사내에서 주목받고 있으며, 나아가 표준으로 자리매김했다. 이와 더불어 요청은 큐에 저장되어진다. 또한 이를 통해 처리량이 늘어난다."
```

**expected**

- `~에 있어서`를 `~에서`로, 이중피동(`저장되어진다`)을 능동(`저장한다`)으로 바꿉니다.
- 공허한 평가(`핵심 역할을 한다`, `자리매김했다`)를 빼거나 실제 동작으로 바꿉니다. 동작을 원문에서 알 수 없으면 추측하지 않고 확인 대상으로 남깁니다.
- 주어 없는 과장(`주목받고 있다`)은 주어나 사실로 바꾸고, 확인할 수 없으면 뺍니다.
- 한 문단에 몰린 접속어(`또한`, `나아가`, `이와 더불어`, `이를 통해`)를 줄여 한두 개만 남기거나 뺍니다.

**must-not**

- `~에 있어서`, 이중피동, 접속어 몰림을 그대로 둡니다.
- 원문에 없는 주체나 수치(사용 팀, 처리량, 성능)를 지어냅니다.
- 모듈의 실제 동작을 확인하지 않고 임의로 구체화합니다.

## 9. 평서문을 요구문으로 (RFC 2119)

`reference/requirement-levels.md`의 규칙이 걸리는지 봅니다. 평서문에 주어와 수준 키워드를 넣고, 금지를 부정 평서문이 아니라 MUST NOT으로 쓰며, 한 문장에 몰린 요구를 나누는지 확인합니다.

**prompt**

```text
아래 보안 명세를 요구문으로 다시 써 줘. 파일을 수정하지 말고 결과만 보고해 줘.

"어떤 결과에도 비밀번호와 비밀번호 해시가 들어 있지 않다. 이메일은 회원마다 다르다. 비밀번호가 8자보다 짧거나 UTF-8로 72바이트보다 길면 거부한다."
```

**expected**

- 주어를 넣고(`시스템은`, `두 회원의 이메일이`) 금지를 **절대 ~해서는 안 된다**(MUST NOT)로 씁니다.
- `A이거나 B이면` 한 문장을 요구 두 개로 나누고 각각 **반드시 ~해야 한다**(MUST)로 씁니다.
- 수치(8자, UTF-8 72바이트)와 단위를 보존합니다.
- `reference/requirement-levels.md`를 근거로 인용합니다.

**must-not**

- 부정 평서문(`들어 있지 않다`)을 그대로 두고 표현만 다듬습니다.
- 두 거부 조건을 한 문장에 유지합니다.
- 8자, 72바이트 수치나 단위를 바꾸거나 `수 있다`를 새로 넣습니다.

## 10. `~할 수 있다`: 허용과 가능성 구분

`~할 수 있다`를 허용(MAY)의 뜻으로만 쓰는지, 능력과 가능성은 다른 말로 바꾸는지 봅니다. 한 문단에 허용 한 문장, 가능성 한 문장을 심었습니다.

**prompt**

```text
아래 문단을 명세 문서에 맞게 고쳐 줘. 파일을 수정하지 말고 결과만 보고해 줘.

"로그인의 응답 시간이 경우마다 다를 수 있다. 관리자는 세션 상한을 바꿀 수 있다."
```

**expected**

- 첫 문장의 `다를 수 있다`는 가능성이므로 `다른 경우가 있다`로 바꿉니다. 허용이 아닙니다.
- 둘째 문장의 `바꿀 수 있다`는 허용(MAY)이므로 그대로 둡니다.

**must-not**

- 두 문장을 똑같이 처리합니다.
- 둘째 문장을 평서문으로 바꿔 허용 수준을 지웁니다.
