# 잘 쓴 보안 요구 명세 (회원 가입)

평서문 초안을 RFC 2119 요구문으로 바꾸고 ASD-STE100 문장 원칙을 적용한 예입니다. 규칙 정본은 [../reference/requirement-levels.md](../reference/requirement-levels.md)입니다.

## 이 문서를 읽는 법

요구의 수준은 **굵은 키워드**로 표시합니다. 굵은 키워드가 없는 문장은 요구가 아니라 설명입니다. 키워드의 뜻은 [../reference/requirement-levels.md](../reference/requirement-levels.md)를 따릅니다.

| 키워드 | 뜻 |
| --- | --- |
| 반드시 ~해야 한다 (MUST) | 예외가 없는 요구 |
| 절대 ~해서는 안 된다 (MUST NOT) | 예외가 없는 금지 |
| ~하는 것을 권장한다 (SHOULD) | 이유가 있으면 따르지 않아도 됩니다. 그 이유를 적습니다 |

## 요구

| 코드 | 요구 | 수준 |
| --- | --- | --- |
| AC-1.4 | 비밀번호가 8자보다 짧으면 가입을 거부한다 | MUST |
| AC-1.4 | 비밀번호가 UTF-8로 72바이트보다 길면 가입을 거부한다 | MUST |
| AC-1.7 | 응답에 비밀번호와 비밀번호 해시를 넣지 않는다 | MUST NOT |
| R6 | 두 회원의 이메일이 같지 않다 | MUST NOT |
| AC-2.1 | 비밀번호 해시에 Argon2id를 쓴다 | SHOULD |

## 요구 문장

- 비밀번호가 8자보다 짧으면 시스템은 **반드시** 가입을 거부**해야 한다**.
- 비밀번호가 UTF-8로 72바이트보다 길면 시스템은 **반드시** 가입을 거부**해야 한다**.
- 시스템은 어떤 응답에도 비밀번호와 비밀번호 해시를 **절대 넣어서는 안 된다**.
- 두 회원의 이메일이 **절대 같아서는 안 된다**.
- 시스템은 비밀번호 해시에 Argon2id를 쓰는 것을 **권장한다**. bcrypt를 쓸 때는 그 이유를 적는다.

## 받아들인 한계

- 로그인의 응답 시간은 경우마다 다른 경우가 있다.

요구가 아니라 관찰한 사실이므로 수준 키워드를 쓰지 않습니다. `다를 수 있다`로 쓰면 허용(MAY)과 섞이므로 `다른 경우가 있다`로 씁니다.

## 평서문에서 요구문으로 (변환 전후)

| 전 (평서문) | 후 (요구문) |
| --- | --- |
| 어떤 결과에도 비밀번호 해시가 들어 있지 않다. | 시스템은 어떤 응답에도 비밀번호 해시를 **절대 넣어서는 안 된다**. |
| 비밀번호가 8자보다 짧거나 72바이트보다 길면 거부한다. | (요구 두 개로 분리) 비밀번호가 8자보다 짧으면 시스템은 **반드시** 거부**해야 한다**. 비밀번호가 72바이트보다 길면 시스템은 **반드시** 거부**해야 한다**. |

적용한 규칙:

1. 주어를 넣습니다(`시스템은`, `두 회원의 이메일이`).
2. 수준 키워드를 넣고 굵게 씁니다.
3. 한 문장에 요구 하나만 담습니다.
4. 숫자에는 단위를 적습니다(자, 바이트).
