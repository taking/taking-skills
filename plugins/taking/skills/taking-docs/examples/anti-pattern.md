# Anti-patterns

reference-first 문서에서 자주 나오는 안티패턴과 교정법.

## Overview

문서가 길고 스캔이 안 되는 원인은 대부분 아래 표에 있습니다. 하나라도 걸리면 해당 열의 "고치는 법"으로 변환합니다.

## Catalog

| 안티패턴 | 왜 나쁜가 | 고치는 법 |
| --- | --- | --- |
| Wall of prose | 5줄 넘는 문단은 핵심을 못 찾습니다 | 3~4줄로 자르고 bullet/표로 분해 |
| No Overview | 첫 화면에서 "무엇/왜"를 못 줍니다 | 맨 위에 TL;DR/Overview 3~6줄 |
| Why-first | 배경부터 늘어놓아 결론이 늦습니다 | What → How → Why 순서로 |
| 중복 서술 | 같은 사실이 여러 곳, 수정 시 어긋남 | single source, 나머지는 링크 |
| 무라벨 코드펜스 | 하이라이트 안 됨, 언어 불명확 | 모든 펜스에 언어 지정 |
| Everything-as-prose | 표로 낼 비교를 문장으로 씀 | 역할, 비교, API, 장단점은 표 |
| AI 문체 | "포장" 단어가 내용을 흐립니다 | 실제 동사, 수치로 대체하거나 삭제 |
| 긴 대시(`—`) | em-dash는 AI 글 표시, 한국어 관습이 아님 | 마침표, 콜론, 괄호로 |
| 부정 대구 | "X가 아니라 Y"는 빈 Y를 숨깁니다 | 거부절을 지우고 Y를 구체적으로 |
| 의의 과장 | "핵심, 전환점, 상징"은 사실을 안 줍니다 | 사실만 쓰고 판단은 독자에게 |
| 3의 법칙 | 항상 셋씩 나열하면 기계적입니다 | 실제 개수대로(2개면 2개) |
| 거짓 범위 | "A부터 Z까지"는 중간이 비었습니다 | 실제 항목을 나열 |
| 강조 분열문 | "핵심은 바로 ~"로 비틀어 강조합니다 | 핵심 내용을 바로 서술 |
| 이중피동 | "~되어진다"는 피동을 겹쳐 씁니다 | `~한다`, `~된다`로 |
| 가운뎃점(`·`) | `·`로 잇는 나열은 AI 글 표시입니다 | 쉼표로, 셋 넘으면 표 |
| 금지를 평서문으로 | 독자가 금지인지 설명인지 모릅니다 | `MUST NOT`(절대 ~해서는 안 된다)로 |
| `~할 수 있다` 오용 | 허용인지 능력인지 섞입니다 | 허용(MAY)에만. 능력, 가능성은 `~하는 경우가 있다`로 |

## 나쁜 예 → 좋은 예

### 무라벨 코드펜스

나쁜 예:

    ```bash
    kubectl get pods -n agent
    ```

좋은 예:

```bash
kubectl get pods -n agent
```

### Everything-as-prose (비교를 문장으로)

나쁜 예:

> tunnel은 동기 통신이고 지연에 민감하며, Kafka는 비동기이고 지연을 허용한다.

좋은 예:

| 전송로 | 통신 | 지연 |
| --- | --- | --- |
| tunnel | 동기 | 민감 |
| Kafka | 비동기 | 허용 |

### AI 문체

나쁜 예:

> 이를 통해 다양한 요청을 효율적으로 처리하는 것이 가능하다.

좋은 예:

> 단일 stream으로 요청을 multiplex합니다.

### 긴 대시(`—`)

나쁜 예:

> 재시작하면 설정을 다시 읽는다 — RBAC는 기동 시점에만 반영된다.

좋은 예:

> 재시작하면 설정을 다시 읽습니다. RBAC는 기동 시점에만 반영됩니다.

### 부정 대구

나쁜 예:

> 이건 캐시 문제가 아니라 설계 문제다.

좋은 예:

> 스키마를 매 요청 재검증해서 느립니다.
