# 한국어 기술 문서 및 코드 주석 작성 규칙

한국어 기술 문서와 코드 주석을 작성, 수정, 번역, 리뷰할 때 이 Skill을 적용합니다. 목표는 **기술적 의미를 정확하게 보존하면서 한국어 개발자가 자연스럽게 읽을 수 있는 문서**를 만드는 것입니다.

## 1. 우선순위

규칙이 충돌하면 다음 순서로 판단합니다.

1. 기술적 정확성과 내용 보존
2. 명확성 및 논리적 완결성
3. 기존 프로젝트의 계약과 관례
4. 문단 응집도와 정보 구조
5. 간결성과 문체

간결하게 만들기 위해 조건, 예외, 근거, 수치, 기술적 맥락을 제거하지 않습니다. 스타일 규칙을 맞추려고 자연스러운 문장을 억지로 바꾸지 않습니다.

## 2. 문서 톤

한 문서 안에서 종결 톤을 섞지 않습니다. 기본 톤은 존댓말이며, 프로젝트에 이미 정한 문체가 있으면 기존 관례를 확인합니다.

| 유형 | 기본 톤 |
| --- | --- |
| 기술 문서, README, ADR, API, 사용자 가이드 | 존댓말 `~합니다` |
| 코드 주석 | 저장소 관례 우선, 존댓말 기본 |
| 짧은 코드 주석 사실 | 필요한 경우 명사형 허용 |
| 커밋 제목 | 명령형 또는 명사형 |

**기존 글을 윤문할 때는 작성자 말투를 보존합니다.** 블로그, 회고, 개인 글처럼 작성자의 구어체나 감정 표현이 담긴 글을 다듬을 때는 위 기본 톤을 강제하지 않습니다. 부자연스럽지 않다면 작성자의 어투, 구어체, 감정, 개성 있는 문장을 유지합니다. 절차는 [workflows.md](workflows.md)의 polish를 참고합니다.

## 3. 기술 문서 작성

문서 작성의 상세 정본은 [style-guide.md](style-guide.md)입니다. 작업에 필요한 부분을 확인합니다.

### 문장과 문단
- 영어 어순을 그대로 옮기지 말고 한국어 문장으로 다시 씁니다.
- 행위 주체와 동작, 조건, 결과를 명확하게 표현합니다.
- 밀접한 문장은 같은 문단으로 묶고, 주제나 논점이 바뀔 때 문단을 나눕니다.
- 한 문장마다 빈 줄을 넣지 않습니다.
- Markdown 원문에서 문단 내부를 편집기 폭에 맞춰 강제로 줄바꿈하지 않습니다. 한 문단은 한 줄로 작성합니다.
- 문단 길이를 문장 수로 기계적으로 제한하지 않습니다. 의미 단위와 응집도를 기준으로 판단합니다.
- 불필요한 접속어, 수식어, 반복 표현을 줄입니다.
- ASD-STE100의 명확성, 일관성, 모호성 제거 원칙을 참고합니다. 공식 표준의 어휘와 문법 규칙을 한국어에 기계적으로 적용하지 않습니다.

### 정보 구조 선택
내용에 가장 적합한 형식을 선택합니다. 표나 다이어그램을 무조건 우선하지 않습니다.

- **문단:** 배경, 판단 근거, 원인과 결과처럼 논리적 연결이 중요한 설명
- **Dash 목록:** 독립된 항목, 책임, 기능, 조건이 여러 개 나열될 때
- **번호 목록:** 순서가 결과에 영향을 주는 절차
- **표:** 같은 기준으로 비교하는 항목, 속성, 값, 계약
- **Mermaid:** 처리 흐름, 조건 분기, 상호작용, 상태 전이, 컴포넌트 관계
- **SVG:** Mermaid로 표현하기 어렵거나 정교한 레이아웃이 필요한 경우

독립 항목이 3개 이상이면 목록을 검토합니다. 목록 항목은 하나의 핵심 내용을 담고, 가능하면 핵심 키워드를 앞에 둡니다. 논리적 연결이 중요한 설명은 목록으로 쪼개지 않습니다. Mermaid를 기본 다이어그램 도구로 사용하고, 짧은 설명 하나를 다이어그램으로 만들지는 않습니다.

### 기술적 정확성
- 조건, 예외, 부정, 순서, 수치, 버전, API 이름, 설정값, 파일명 및 식별자를 보존합니다.
- 구현에서 확인한 사실, 설계 의도, 추론을 구분합니다.
- 확인하지 않은 동작이나 수치를 추측해 채우지 않습니다.
- 기존 용어와 프로젝트 고유 명칭을 임의로 바꾸지 않습니다.
- 문서 종류에 맞는 템플릿을 참고하되, 실제 저장소의 관례와 독자 목적을 확인합니다.

### 문체
- 모호한 표현은 구체적인 조건으로 바꿉니다. 근거가 없으면 임의로 구체화하지 않습니다.
- `이를 통해`, `효율적으로`, `손쉽게`, `다양한`, `수행한다`, `제공한다` 같은 표현은 정보가 없으면 실제 동작으로 바꾸거나 삭제합니다.
- 긴 대시(`—`), 습관적인 부정 대구, 강조 분열문(`중요한 것은 ~`, `핵심은 바로 ~`), 근거 없는 과장과 3개 맞춤 나열을 피합니다.
- 업계 표준 기술 용어와 코드 식별자는 정확성을 위해 유지합니다.
- 문체를 다양하게 보이려고 종결어미를 억지로 바꾸지 않습니다.

### 명세와 요구 문장
시스템 제약, 아키텍처 규칙, API 계약, 보안 요구처럼 지켜야 하는 수준이 있는 문장은 RFC 2119와 ASD-STE100 원칙을 함께 적용합니다. 정본은 [reference/requirement-levels.md](reference/requirement-levels.md)입니다.

- 요구에는 수준 키워드를 **굵게** 씁니다. MUST(반드시 ~해야 한다), MUST NOT(절대 ~해서는 안 된다), SHOULD(~하는 것을 권장한다), MAY(~할 수 있다).
- `~할 수 있다`는 허용(MAY)의 뜻으로만 씁니다. 능력과 가능성은 다른 말로 씁니다.
- 명세 문장은 주어를 적고 능동으로 쓰며, 한 문장에 요구 하나만 담습니다.

## 4. 코드 주석

코드 주석 규칙의 정본은 [code-comments/style-guide.md](code-comments/style-guide.md)입니다. 리뷰할 때는 해당 규칙과 언어별 규칙을 확인합니다.

핵심 원칙:
- 주석보다 코드, 이름, 구조를 먼저 개선합니다.
- 주석은 코드에서 알 수 있는 WHAT을 반복하지 않고, 코드만으로 알 수 없는 WHY와 계약을 설명합니다.
- 주석을 삭제했을 때 다음 유지보수자가 코드를 잘못 변경할 위험이 있는지 판단합니다.
- 공개 API, wire 계약, 불변식, 보안 경계, 동시성, 실패 모드, 성능 최적화, workaround는 필요한 근거를 문서화합니다.
- 계약, 불변식, 보장을 서술할 때는 요구의 수준(MUST/SHOULD/MAY)을 고정합니다. 정본은 [reference/requirement-levels.md](reference/requirement-levels.md)이며, wire와 공개 API 주석에서는 영어 RFC 2119 키워드를 그대로 씁니다.
- 설계 서사, 과거 구현 회고, 단순한 문법 해설은 코드 주석에 넣지 않습니다.
- 언어 표준 형식(GoDoc, Javadoc, JSDoc 등)을 따릅니다.
- 저장소의 기존 종결 톤을 확인하고 일관되게 작성합니다.

주석 리뷰 순서:
1. 코드 개선
2. 이름 개선
3. 불필요한 주석 삭제
4. 남길 주석 재작성
5. 필요한 계약과 WHY 추가

## 5. 커밋, PR, 작업 보고서

커밋과 PR 형식의 정본은 [reference/commit-pr.md](reference/commit-pr.md)입니다.

- 커밋 제목은 프로젝트 형식과 타입 접두사를 따르고 간결하게 작성합니다.
- 커밋 본문과 PR은 변경 이유와 핵심 변경 사항을 중심으로 작성합니다.
- 코드만으로 알 수 있는 구현 과정을 장황하게 반복하지 않습니다.
- AI 서명, 과장, 제목과 본문의 중복을 넣지 않습니다.

Jira 댓글, MR 본문, 작업 완료 보고서처럼 끝난 작업을 전달하는 글은 [reference/work-report.md](reference/work-report.md)가 정본입니다.

- 문장만 다듬지 않고 작업 결과, 변경 사항, 설계 근거, 검증 결과, 미완료 항목이 구분되도록 구조를 다시 짭니다.
- 무엇을 바꿨는지만 적지 않고 기존 방식의 문제와 이 방식을 고른 이유를 함께 적습니다.
- 시험 작성, 시험 실행, 빌드 통과, 실환경 확인을 구분합니다. 하지 않은 검증은 하지 않았다고 적습니다.

## 6. 작업별 절차

작업 유형에 맞는 절차를 [workflows.md](workflows.md)에서 선택합니다.

- **write:** 문서 종류와 독자를 확인하고 템플릿 및 기존 문서를 살펴본 뒤 작성합니다.
- **review:** 정확성, 논리, 구조, 문체 순으로 문제를 찾고 필요한 부분만 수정합니다.
- **rewrite:** 원문의 사실과 값을 먼저 추출하고 문단, 목록, 표, 다이어그램으로 재구성한 뒤 원문과 대조합니다.
- **polish:** 기존 글의 의미, 사실관계, 작성자 말투를 보존하면서 AI 문체와 번역투만 최소한으로 다듬습니다. 수정본, 주요 수정 사항, 확인이 필요한 부분으로 보고합니다.
- **work report:** 작업 메모나 초안을 Jira 댓글, MR 본문, 작업 완료 보고서로 재구성합니다. 절차는 [workflows.md](workflows.md), 규칙은 [reference/work-report.md](reference/work-report.md)입니다.
- **code comment review:** 코드 개선 가능성을 먼저 확인한 뒤 주석을 유지, 삭제, 재작성, 추가합니다.

사용자가 전체 파일 수정을 요청하면 제안만 하지 말고 실제 파일을 수정하고 링크, 코드, 수치 및 내용 보존 여부를 검증합니다. 사용자가 검토만 요청했다면 파일을 임의로 수정하지 않습니다.

## 8. 검증

- 문서 제출 전 [checklist.md](checklist.md)를 확인합니다.
- Markdown 파일은 `scripts/lint-docs.sh <경로>`로 검사합니다.
- 코드 주석은 `scripts/lint-comments.sh <경로>`로 검사합니다.
- 자동 검사는 정규식으로 판정할 수 있는 항목만 다룹니다. 기술적 정확성, 논리, 자연스러운 문체는 별도로 검토합니다.
- 규칙을 수정하면 관련 예제와 `evals/README.md`의 기대 결과도 함께 확인합니다.
