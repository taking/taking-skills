# 작업 보고서 규칙

Jira 댓글, MR 본문, 작업 완료 보고서처럼 **끝난 작업을 남에게 전달하는 글**의 규칙입니다. 읽는 사람은 다른 개발자, 리뷰어, 기술 책임자이고, 별도 설명 없이 작업 범위와 변경 이유, 검증 수준을 알 수 있어야 합니다.

문체, 번역투, 표 선택, 용어 규칙은 [style-guide.md](../style-guide.md)와 [translationese.md](translationese.md)가 정본입니다. 여기에 다시 적지 않습니다. 커밋 제목과 PR 형식은 [commit-pr.md](commit-pr.md)가 가집니다.

## 1. 맞춤법 교정이 아닙니다

원문의 기술적 사실을 유지하면서 **구조를 다시 짭니다**. 작업 결과, 변경 사항, 설계 근거, 검증 결과, 미완료 항목이 각각 어디 있는지 읽는 사람이 찾을 수 있어야 합니다.

문장만 다듬고 구조를 그대로 두면 "무엇을 했는지"는 보이지만 "왜 그렇게 했는지"와 "어디까지 확인했는지"가 묻힙니다. 보고서에서 그 둘이 빠지면 리뷰어가 같은 질문을 다시 합니다.

## 2. 변경 이유를 반드시 적습니다

무엇을 바꿨는지만 적지 않습니다. **기존 방식의 무엇이 문제였고, 왜 이 방식을 골랐는지**를 함께 적습니다.

| 적는 것 | 예 |
| --- | --- |
| 기존 동작과 그 문제 | 상한을 넘긴 요청이 거절되지 않고 대기열에서 기다려, 상한에 걸린 사실이 드러나지 않았습니다 |
| 실제 고친 방식 | 클러스터별 상한을 켜서 49번째 요청을 거절합니다 |
| 그 방식을 고른 이유 | 터널 웹소켓 연결 상한과 같은 값이라 두 상한이 어긋나지 않습니다 |
| 검토했으나 버린 방식 | 태그 재작성은 재연결 뒤 게이지가 닫힌 풀을 읽어 뺐습니다 |

버린 방식을 적는 이유는 리뷰어가 같은 안을 다시 제안하지 않게 하기 위해서입니다. 검토하지 않은 안을 검토한 것처럼 적지는 않습니다.

## 3. 검증 수준을 구분합니다

**구현한 것과 검증한 것은 다릅니다.** 아래 넷은 서로 다른 수준이고, 섞어 적으면 읽는 사람이 실제보다 많이 확인했다고 오해합니다.

| 수준 | 뜻 |
| --- | --- |
| 시험 작성 | 시험 코드를 썼습니다. 돌렸는지는 별개입니다 |
| 시험 실행 | 단위 시험이나 통합 시험이 통과했습니다 |
| 빌드와 정적 분석 | 컴파일, lint, CI Pipeline이 통과했습니다 |
| 실환경 확인 | 실제 환경에 올려 동작을 눈으로 확인했습니다 |

하지 않은 검증은 **하지 않았다고 적습니다.** 빈칸으로 두거나 통과로 쓰지 않습니다. 재지 못한 이유와 재려면 무엇이 필요한지를 함께 적으면 다음 사람이 이어받을 수 있습니다.

## 4. 기존 설계 의도를 보존합니다

- 주석, Javadoc, ADR, 기존 문서에 적힌 설계 의도는 변경의 근거로 씁니다.
- 설계 의도와 실제 구현이 다르면 그 차이를 적습니다. 어느 쪽을 기준으로 고쳤는지도 적습니다.
- 새 정책이나 설계 결정을 보고서에서 처음 만들지 않습니다. 결정이 필요하면 ADR로 남깁니다.
- 기존 동작을 바꿨으면 전후 차이와 이유를 함께 적습니다.

## 5. 기본 구조

아래 순서를 기본으로 하되, 해당하지 않는 절은 뺍니다. 빈 절을 만들지 않습니다.

| 절 | 언제 쓰나 | 담는 것 |
| --- | --- | --- |
| 작업 완료와 병합 현황 | 항상 | 완료 여부, 저장소, MR 번호와 링크, Commit, 병합 대상 브랜치 |
| 릴리스 | 릴리스가 있을 때 | 버전, 이미지와 차트 발행 여부, 실패와 재작업 경위 |
| 작업 범위 | 점검 범위와 수정 범위가 다를 때 | 전체 점검 건수, 발견 건수, 실제 수정 건수, 후속으로 남긴 것 |
| 구현 요약 | 코드 변경이 있을 때 | 주제별 변경과 그 이유 |
| 문서 현행화 | 문서를 고쳤을 때 | 파일 경로와 변경 내용 |
| 검증 | 항상 | 실제 실행한 것과 결과, 미실행 |
| 정본과 다르게 구현한 부분 | Task, ADR, 설계 문서와 다를 때만 | 정본 내용, 실제 구현, 다르게 한 이유와 근거 |
| 리뷰 반영 | 리뷰에서 추가로 고쳤을 때 | 발생 조건과 수정 내용 |
| 범위 밖으로 남은 항목 | 남은 것이 있을 때 | 미처리 항목, 제외 이유, 후속 조건 |

여러 저장소에 걸친 작업은 MR 현황을 표로 모읍니다.

```markdown
| 저장소 | MR | 주요 변경 |
| --- | --- | --- |
```

변경 전후를 설명할 때는 표를 먼저 검토합니다. 다만 배경과 판단 근거가 필요한 변경은 표 대신 하위 제목과 문단을 씁니다.

```markdown
| 항목 | 기존 동작 | 변경 내용 |
| --- | --- | --- |
```

릴리스에서 실패와 재작업이 있었으면 최초 실패, 원인, 수정, 최종 결과를 구분합니다. 수행하지 않은 릴리스 단계를 완료한 것처럼 적지 않습니다.

## 6. 표를 다룰 때

[style-guide.md](../style-guide.md) §4가 정본입니다. 보고서에서 자주 생기는 것만 더 적습니다.

- 원문의 깨진 Markdown 표는 정상 표로 복원합니다. 깨진 채로 두거나 문단으로 풀어 버리지 않습니다.
- 성격이 다른 변경을 한 표에 억지로 모으지 않습니다. 열 제목이 어느 행에는 맞지 않으면 표를 나눕니다.
- 빈 표, 빈 행, 의미 없는 구분선을 남기지 않습니다.

## 7. 출력 규칙

- 원문을 요약하지 말고 보고서 전체를 다시 씁니다.
- 받은 기술적 세부 사항을 임의로 줄이지 않습니다. 줄여야 하면 무엇을 뺐는지 밝힙니다.
- 바로 Jira 댓글이나 MR 본문에 붙여 넣을 수 있는 Markdown 으로 냅니다.
- 작성 의도나 설명을 본문에 섞지 않습니다.
- 부족한 정보를 임의로 채우지 않습니다.
- 기술적으로 의심스러운 곳은 본문을 고치지 말고 결과물 아래에 `추가 확인 사항`으로 따로 적습니다.
- 사용자가 형식을 지정하지 않으면 기존 보고서 템플릿을 그대로 씁니다. 저장소에 정본 템플릿이 있으면 그것이 우선입니다.

## 8. 제출 전 점검

[checklist.md](../checklist.md)를 먼저 확인하고, 보고서에만 해당하는 아래를 더 봅니다.

- [ ] 작업 결과와 실제 변경 내용이 구분되는가?
- [ ] 기존 동작과 변경 후 동작의 차이가 적혀 있는가?
- [ ] 주요 기술적 판단에 근거가 있는가?
- [ ] 시험 작성, 시험 실행, 빌드 통과, 실환경 확인을 혼동하지 않았는가?
- [ ] 미검증 항목과 범위 밖 항목이 구분되어 있는가?
- [ ] MR 번호, Commit, 버전, 함수명, 파일 경로, 오류 코드에 오타가 없는가?
- [ ] 원문에 없는 효과나 사실을 더하지 않았는가?
