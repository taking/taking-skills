# 요구의 수준과 명세 문장 (RFC 2119 + ASD-STE100)

시스템 제약, 아키텍처 규칙, API 계약, 보안 요구처럼 **지켜야 하는 수준이 있는 문장**을 쓸 때 적용합니다. 두 표준은 서로 다른 것을 다룹니다.

| | RFC 2119 | ASD-STE100 |
| --- | --- | --- |
| 다루는 것 | 요구의 수준 (필수, 금지, 권장, 허용) | 문장의 모양 (짧게, 능동태, 한 개념에 한 용어) |
| 답하는 질문 | "어겨도 되는가?" | "무슨 뜻인가?" |
| 단위 | 키워드 | 문장 전체와 낱말 |

RFC 2119는 요구의 **수준**을 키워드로 고정하고, ASD-STE100은 그 문장의 **모양**을 정합니다. 명세 문장 하나에 두 표준을 함께 적용합니다. 설명, 배경, 개요 문장에는 적용하지 않습니다.

## 1. 요구의 수준 (RFC 2119)

요구의 수준을 나타내는 낱말의 뜻은 [BCP 14](https://www.rfc-editor.org/info/bcp14)(= [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) + [RFC 8174](https://www.rfc-editor.org/info/rfc8174))가 고정합니다. RFC 8174는 **대문자 키워드일 때만** 규범적 의미를 가진다고 명확히 합니다. 한국어 문서에서는 이 구분을 **굵게**로 표시합니다. 굵지 않은 같은 낱말은 요구가 아니라 설명입니다. 코드 주석에서는 키워드를 영어로 쓰고 굵게나 표 없이 소스 관례(GoDoc, JavaDoc)를 따릅니다([../code-comments/style-guide.md](../code-comments/style-guide.md) §14). 키워드는 다음과 같이 대응시킵니다.

| 키워드 | 한국어 | 뜻 |
| --- | --- | --- |
| MUST | 반드시 ~해야 한다 | 예외가 없는 요구 |
| MUST NOT | 절대 ~해서는 안 된다 | 예외가 없는 금지 |
| SHOULD | ~하는 것을 권장한다 | 이유가 있으면 따르지 않아도 됩니다. 그 이유를 적습니다 |
| MAY | ~할 수 있다 | 허용. 해도 되고 하지 않아도 됩니다 |

### 요구의 수준을 쓰는 일곱 가지 규칙

1. 키워드는 **굵게** 씁니다. 굵은 말이 없는 문장은 요구가 아니라 설명입니다.
2. `~할 수 있다`는 **허용(MAY)의 뜻으로만** 씁니다. 능력과 가능성에는 다른 말을 씁니다 (`다를 수 있다` → `다른 경우가 있다`).
3. 금지는 **MUST NOT**으로 씁니다. 부정의 평서문(`들어 있지 않다`)으로 쓰지 않습니다.
4. 요구를 표로 정리할 때는 `수준` 열을 둡니다. 열의 값과 문장의 키워드가 같아야 합니다.
5. 키워드는 **요구에만** 씁니다. 용어의 표, 맥락, 결과, 버린 대안에는 쓰지 않습니다.
6. 원래 문장에 없던 권장이나 허용을 새로 만들지 않습니다. 윤문으로 요구의 수준을 바꾸지 않습니다.
7. 문서 머리에 `이 문서를 읽는 법`을 둡니다. 키워드 표는 한 문서에만 두고, 다른 문서는 그 문서를 가리킵니다.

## 2. 명세 문장 (ASD-STE100의 원칙)

[ASD-STE100](https://www.asd-ste100.org/)은 항공기 정비 문서에서 나온 기술 영어 표준으로, 영어가 모국어가 아닌 사람도 틀리지 않게 읽도록 만들었습니다. STE100의 사전은 영어의 사전이라 낱말은 한국어로 옮길 수 없습니다. 문장의 모양을 정하는 **원칙만** 옮깁니다.

### 명세 문장을 쓰는 다섯 가지 규칙

1. **주어를 적습니다** (`시스템은`). 능동으로 씁니다.
2. **한 문장에 요구는 하나입니다.** `A이거나 B이면`은 두 문장으로 나눕니다.
3. **한 개념에 한 용어**를 씁니다. 용어는 해당 도메인 문서의 용어 표를 따릅니다.
4. **범위가 흐린 말을 쓰지 않습니다** (`비어 있다`, `올바른`, `구분할 수 없는`). 뜻을 정하거나, 정하지 않았다고 적습니다.
5. **숫자에는 단위를 적습니다** (자, 바이트, 코드 포인트). 숫자의 출처를 적습니다.

원문 규칙에서 절차 문장은 20단어, 설명 문장은 25단어까지로 제한하지만, 한국어에는 단어 수를 기계적으로 적용하지 않고 `한 문장에 요구 하나`를 기준으로 봅니다.

## 3. 평서문을 요구로 바꾸는 예

평서문은 요구의 수준이 빠진 문장입니다. 주어와 수준의 키워드를 넣어 요구로 바꿉니다.

| 적용 규칙 | 전 (평서문) | 후 (요구) |
| --- | --- | --- |
| 주어 + 수준 | 어떤 결과에도 비밀번호와 비밀번호 해시가 들어 있지 않다. | 시스템은 어떤 결과에도 비밀번호와 비밀번호 해시를 **절대 넣어서는 안 된다**. |
| 주어 + 수준 | 이메일은 회원마다 다르다. | 두 회원의 이메일이 **절대 같아서는 안 된다**. |
| 요구 하나씩 | 비밀번호가 8자보다 짧거나, UTF-8로 72바이트보다 길면 거부한다. | 비밀번호가 8자보다 짧으면 시스템은 **반드시** 가입을 거부**해야 한다**. 비밀번호가 UTF-8로 72바이트보다 길면 시스템은 **반드시** 가입을 거부**해야 한다**. |
| `수 있다`는 허용만 | 로그인의 응답 시간이 경우마다 다를 수 있다. | 로그인의 응답 시간은 경우마다 다른 경우가 있다. |

## 4. 역할 구분

전역 규칙(`~/.claude/CLAUDE.md`)은 **무엇을 따를지**를 말합니다. 프로젝트의 문서 작성 가이드는 **어떻게 쓸지**를 말합니다. 이 reference는 어떻게 쓸지의 정본입니다.

- 전역: 명세에는 RFC 2119를, 사용자 가이드와 런북, 오류 메시지, 운영 지침에는 ASD-STE100 원칙을 따른다.
- 프로젝트: 위 12개 규칙으로 실제 문장을 쓰고, 도메인 용어 표와 요구 표를 둔다.
